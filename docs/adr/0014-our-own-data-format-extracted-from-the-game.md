# Data versions use our own format, written by `aic-extract` from the game's tables

A data version was factoriolab's `data.json`, copied as it was (`data/v1.5.3.json`), with an overlay beside it for what factoriolab's format can't say. It becomes our own format, defined once in `aic-data` (`aic_data::file`), with one loader. `v1.5.3.json` was converted to it once, by hand; `v1.6.0.json` and every later version are written by a new crate, `aic-extract`, from the tables the game client ships, which the user exports and copies in by hand. The format's reference is `data/README.md`.

Two reasons:

- **The game's tables say what factoriolab's data had to be told.** They have each item's phase (solid, liquid or gas), each transmuting unit's activation input as its own table (ADR 0013), the gas environment a recipe needs, the outposts' prices and the belt and pipe speeds. factoriolab's format has no place for the first three, so the app guessed fluids from ID prefixes and the overlay carried the activation inputs. A format of our own holds them as data.
- **factoriolab's recipe IDs and inputs were its own.** Its recipe IDs (`copper_nugget`) were made up, four of its item IDs too (`iron_bottle-liquid_plant_grass_1`), and it folded each activation input into the recipe as an ordinary input, which the overlay then had to take apart again. The game names its crafts (`furnance_copper_nugget_1`) and lists the activation input apart from them.

## Considered Options

- **Keep factoriolab's format and grow the overlay.** Rejected: every new version would need the overlay rewritten by hand for what the tables already say (activation inputs, phases, environments), with the same folding taken apart again, and a second source of truth for each.
- **The game's own IDs for everything, items and facilities included** (`item_copper_nugget`, `furnance_1` as building; `component_mc_1` where we say `cmpt_mc_1`). Rejected: every icon file is named by our IDs (ADR 0012) and every saved graph holds them, so it would rename every icon and break every saved graph for no gain. Items keep the game's ID without `item_`, facilities the ID of the item that places them without `item_port_`, and regions stay `tundra` and `jinlong`. Recipes take the game's craft IDs, which the old data never had.
- **An extractor that reads the factoriolab data, or a wiki.** Rejected: the game's tables are the source both of those copy from, and they are current (v1.6.0, where factoriolab stopped at v1.5.3).

## Consequences

- A file holds IDs and numbers, never names; names stay the app's tables (ADR 0012). `aic-extract` adds the English names the game gives to `crates/aic-editor/i18n/names/en.json` where the table has none. It never changes a name the table has, with two exceptions: a facility that is a building of the game takes the game's name, and a recipe the game names like another takes ours: `Packaged <fluid> (<container>)` and `Unpackage <fluid> (<container>)` for filling a container and emptying it, and otherwise the game's name with what sets the recipe apart in brackets (an input, or the gas environment it needs). A missing name falls back to the ID: the Chinese-name fallback is gone with the format.
- **Aliases.** A version may map an older version's IDs to its own (`aliases.items`, `aliases.recipes`). `Graph::rebind`, which every open and every data switch goes through, follows them, so a graph saved on v1.5.3 opens on v1.6.0 with its recipes and items renamed. `aic-extract --previous` writes them: a recipe whose ID is gone maps to the one new recipe on the same facilities with the same items at the same rates. The previous version's own aliases are carried forward, so every older ID still maps in one hop: one whose target was renamed in this run points at the new ID, and one whose target is gone with nothing in its place is left out and reported. There is no way back: a graph saved on v1.6.0 shows its renamed recipes as missing on v1.5.3.
- **Activation inputs are listed apart from the recipe in the file, as the game does**, on the facility (`"activation": { "item": …, "per_min": … }`), and the loader adds them to every recipe of the facility. So the `Catalog` keeps ADR 0013's invariant (a recipe's inputs are the totals for one facility flat out, the activation input among them) and `aic-core` did not change. Facilities of one recipe that disagree on it are a load error.
- **Facilities are no longer items.** `Catalog::items()` lists items only; a facility's name still comes from the names table's `items`.
- **The overlay stays, in the file's own entries**: `items`, `facilities` and `recipes`, each with `add`, `replace` and `remove`. Its `facility_speeds` and `facility_activation` are gone: a `facilities.replace` says both. v1.5.3's overlay is gone, its activation inputs now in its file.
- An item's phase replaces the `liquid_`/`gas_` prefix rule; its colour is in the file (copied from the previous version by `aic-extract`, none for new items). `Catalog::icon` and factoriolab's sprite-sheet rectangles are gone.
- Trades are marked `"kind": "trade"` rather than recognised from a flag and their shape; mining recipes `"kind": "mining"`, and one may take an input (the Hydro Mining Rig's water).
- A recipe can name the gas environment it needs (`environment`). The catalog carries it; nothing uses it yet (PLAN.md, Gas environments).
- `aic-extract` makes a few assumptions the tables don't settle, listed in `data/README.md`: which liquids a pump lifts as raw resources, `consumeRate` as per minute for the Gas Dispersing Unit, the sewage outlet's time, and a trade's time.
